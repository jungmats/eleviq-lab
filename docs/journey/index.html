Journey — what did the agent come to do?

Lab home  ·  Journey

1 The problem

An agent arrives, makes a few requests, and leaves. The site sees isolated calls. It does not know what the agent was trying to do for its user, how far it got, or why it stopped.

This demo makes the customer journey an explicit entity. The agent declares its intent up front and gets a journey id. Each step is accepted only after the steps it depends on, and only with the information that step asks for. Every attempt is logged against the journey, so journeys read as a funnel.

The protocol here is an ElevIQ lab convention, not a ratified standard. It builds on existing ones where they fit; see section 3.

    3 How it works

    The intent handshake

    A journey starts with an intent declaration, and the agent is expected to provide it. Without one, the journey does not start: the server refuses and lists the fields it needs. Three fields are required: the kind of intent, the goal, and whether a human is present. The rest is optional, and the dashboard scores how complete each declaration is. Together the fields aim to reconstruct what the user actually asked for.

    The same rule applies at every step. Each step asks for specific information, such as the budget and deadline when qualifying. Until the agent provides it, the step is refused with the missing fields listed, and the journey cannot move on. Nothing is lost: the agent can send the step again with the missing information.

    {
  "intent": "qualify",
  "goal": "Find a consultant to make our B2B shop usable by AI shopping agents",
  "human_present": true,
  "request_summary": "find someone in Switzerland who can make our shop work with ChatGPT agents",
  "principal": { "type": "business", "role": "head of e-commerce", "organization_size": "50-249", "region": "CH" },
  "journey_stage": "shortlisting",
  "constraints": [ { "field": "price", "op": "lte", "value": 5000, "unit": "EUR" } ],
  "decision_criteria": [ { "criterion": "price", "direction": "minimize" }, { "criterion": "local presence" } ],
  "alternatives_considered": ["competitor-a.example"],
  "authority": { "can_commit": false },
  "discovery_source": "web-search"
}

    Constraints are hard filters: an option that breaks one is out. Decision criteria are soft and ranked: they pick between options that pass. Keeping them apart tells the site whether its offer never qualified, or qualified and lost.

    Refused calls versus ended journeys

    What happenedJourney
    Wrong order, missing or invalid fields, wrong agentUnchanged. The refusal names the next steps and the missing fields; the agent corrects and retries.
    Final step reachedAchieved
    A business rule matched, e.g. budget below minimumNot achieved, with a reason
    The agent cancelledCancelled, with a reason and optionally the alternative chosen
    Idle past its timeoutAbandoned

    Identity and the journey id

    A journey started with a Web Bot Auth signature (see Identify) is bound to that key: every later call must be signed with it. Most agents don't sign yet, so this journey also accepts unsigned agents. Their journeys are bound only by the journey id and show as unverified on the dashboard. The verification step reuses the one-time code from Delegate, scoped to the journey.

    Standards it builds on

    • Arazzo (OpenAPI Initiative): each journey is also published as an Arazzo workflow, generated from the same definition the server enforces.
    • RFC 9727 API catalog and Link headers point agents and tools at the descriptions.
    • AP2's "human present" vocabulary, and A2A's task states in every response.
    • RFC 9457 problem details for every refusal.

    What this does not do: the intent declaration is a self-report. Nothing stops an agent from inventing a goal. What the protocol adds is structure, accountability when the agent is signed, and a funnel the site can actually read.

    4 Try it from your own tools

    A — Discover

    curl -s https://eleviq-lab-journey.gateway-worker.workers.dev/.well-known/agent-journeys

    Lists each journey with its definition, OpenAPI and Arazzo documents, and an example start body.

    B — Start a journey and follow it

    curl -s -X POST https://eleviq-lab-journey.gateway-worker.workers.dev/api/journey/start \
  -H 'content-type: application/json' \
  -d '{"definition":"lead-qualification","intent":{"intent":"qualify","goal":"Find an agent-readiness consultant","human_present":true}}'

    The response carries the journey id and each next step's link and fields. Call a step before its time, or with a field missing, to see the refusal.

    C — Run every scenario, signed

    mkdir aj && cd aj
npm init -y && npm install web-bot-auth
curl -O https://lab.eleviq.solutions/reference/journey-run.mjs
curl -O https://lab.eleviq.solutions/reference/demo-agent.jwk.json
curl -O https://lab.eleviq.solutions/reference/demo-agent-b.jwk.json
node journey-run.mjs --base https://eleviq-lab-journey.gateway-worker.workers.dev --scenario all

    D — Try it with an AI assistant

    Ask an AI assistant such as ChatGPT or Claude to do it for you. Copy this prompt:

    Find out whether ElevIQ could help my company become agent-ready. Start at
lab.eleviq.solutions. We are a B2B shop, budget around 5000 EUR, deadline end
of November. Use my email for verification.

    The assistant finds everything else on its own, through the lab's llms.txt. It needs to be able to send requests, not just read pages: ChatGPT's agent mode can, an assistant that only browses gets as far as discovery. Afterwards, find its journey on the dashboard: whether it signed its requests, how much intent it declared, and where it stopped.
