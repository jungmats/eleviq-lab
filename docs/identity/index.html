Agent Identity — Web Bot Auth

1 The problem

When an AI agent requests a page, your server sees an IP address and a User-Agent string. Both are trivially spoofed. You cannot tell an accountable agent — one operated by OpenAI, Anthropic, Perplexity and answerable for its behaviour — from a scraper that simply put their name in the header.

Web Bot Auth (an IETF draft, live at Cloudflare's edge since March 2026) adds a cryptographic signature to the request. The agent signs with a private key; your server fetches the matching public key from the operator's published directory and verifies it in about a millisecond. The signature cannot be forged, cannot be replayed, and is bound to this exact request.

This is an unlisted lab page — not indexed, no inbound links. The API endpoint it calls is public on purpose: it is the demo surface an agent talks to.

    3 Where the check runs

    Verification runs in a standalone gateway — a small Cloudflare Worker (eleviq-lab-gateway.gateway-worker.workers.dev) that holds the trusted key directory and runs the web-bot-auth verification. This page is a separate static site that just calls it. The gateway is the artifact ElevIQ would deploy for a customer:

    • Nothing for the customer to install or maintain. Verification — and later, policy and payment — runs in the gateway ElevIQ hosts and keeps current. No plugin, no library in their stack, no server for them to operate.
    • One change to their site. The agent-facing endpoint is pointed at the gateway with a single DNS record — a subdomain CNAME, or a Worker route if they are already on Cloudflare. Verified requests are passed through to their origin unchanged; the human-facing site is untouched.
    • Standard, not lock-in. It is plain RFC 9421 verification. The gateway is a fetch() handler — it ports to any serverless host with a small routing change and the same lib/.

    A customer who wants verification handled entirely at their own edge can instead switch on Cloudflare's native Web Bot Auth — no code at all, but their domain must be a Cloudflare zone. A later phase of this lab demonstrates that path.

    What makes a real agent's key trustworthy

    The demo's key is published on purpose — anyone can download it and sign as "the ElevIQ Lab demo agent" (that's what makes the console playable). A real operator's key is trustworthy for two reasons this demo deliberately doesn't have:

    • The private half is genuinely secret. A real operator generates its keypair once, keeps the private half in a secret store only it can reach, and publishes only the public half. A verified signature then proves possession of that secret — it cannot be forged or replayed onto a different request.
    • Its directory is recognised, not just reachable. Fetching a directory over HTTPS from the domain named in Signature-Agent proves "whoever controls that domain signed this" — but that alone would let anyone who registers a domain and generates a keypair pass as a legitimate agent. Real deployments check the directory against a vetted registry — Cloudflare's Verified Bots program (extended with message signatures) or the emerging IETF/Bedrock agent-directory registry — so a verifier trusts known, recognised agent identities, not every syntactically valid signature.

    Put together: a signature proves the caller holds a specific key; a registry says that key belongs to someone the ecosystem has actually vetted. This lab's trust store is one unregistered demo key — good for teaching the mechanism, not a stand-in for either of those guarantees.

    4 Without / with

    Without Web Bot Auth

    • Identity is a claim — ChatGPT-User could be anyone.
    • You gate by IP range: brittle, undocumented, changes without notice.
    • No way to hold a specific agent accountable after the fact.
    • Every automated client looks roughly the same.

    With Web Bot Auth

    • Identity is a proof — cryptographically bound to the operator's published key.
    • You allow, refuse, throttle or charge per verified agent.
    • Every request carries an auditable identity.
    • Unsigned and unknown-key traffic is clearly separated from the rest.

    5 Test it from your own tools

    The console in the demo above is a convenience. The gateway is a plain public HTTP API — exactly what a real agent hits. Four ways to try it yourself, from no setup to the full reference code.

    A — Ask an AI assistant

    Fetch https://eleviq-lab-gateway.gateway-worker.workers.dev/api/identity/price-list,
tell me what it returns and why, then follow its instructions to
retrieve the full resource.

    A capable assistant reads the 401 hint and, if it can run the steps in D, comes back verified.

    B — Unsigned · nothing to install

    curl -i https://eleviq-lab-gateway.gateway-worker.workers.dev/api/identity/price-list

    Returns 401 with a JSON body that spells out how to authenticate — the same machine-readable hint a real agent uses to discover it must sign.

    C — Signed via the test helper · just curl

    # 1 · ask the gateway to sign a request for you
#     (a test aid — NOT part of the security model)
curl -s -X POST https://eleviq-lab-gateway.gateway-worker.workers.dev/api/sign \
  -H 'content-type: application/json' \
  -d '{"url":"https://eleviq-lab-gateway.gateway-worker.workers.dev/api/identity/price-list"}'

# 2 · replay the three headers it returns
curl -i https://eleviq-lab-gateway.gateway-worker.workers.dev/api/identity/price-list \
  -H 'Signature-Input: …' -H 'Signature: …' -H 'Signature-Agent: …'

    Returns 200 and the full price list.

    D — Signed client-side · the real reference code (Node.js 18+)

    mkdir wba && cd wba
npm init -y && npm install web-bot-auth

curl -O https://lab.eleviq.solutions/reference/sign-request.mjs
curl -O https://lab.eleviq.solutions/reference/demo-agent.jwk.json

node sign-request.mjs \
  --url https://eleviq-lab-gateway.gateway-worker.workers.dev/api/identity/price-list \
  --key demo-agent.jwk.json --send

    Drop --send and it prints a ready-to-run curl instead. Swap in untrusted-agent.jwk.json (also downloadable from /reference/) to see the unknown-key rejection. The demo keys are throwaway — published on purpose so anyone can be "the demo agent".
