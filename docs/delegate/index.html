1 The problem

An agent can be genuinely verified, and genuinely allowed to do something, and still be lying about who it's doing it for — nothing about a valid signature or a permitted purpose says which person the agent claims to represent.

This demo checks that claim: an agent acting for a specific email address only gets access once it presents a one-time code sent to that address — proof of an inbox, not proof that an email address was typed correctly.

The code is genuinely emailed — nothing here shows it to you. Use an email address you can actually check to try the full flow.

    3 Test it from your own tools

    The console above is a convenience. The gateway is a plain public HTTP API — two calls, both signed the same way.

    A — Request a code

    # sign with your agent key (see /api/sign for a test-aid signer)
curl -s -X POST https://eleviq-lab-gateway.gateway-worker.workers.dev/api/delegate/request-code \
  -H 'Signature-Input: …' -H 'Signature: …' -H 'Signature-Agent: …' \
  -H 'content-type: application/json' \
  -d '{"acting_for":"you@example.com"}'

    Emails the code to acting_for — it's never in this response. Use an address you can check; the endpoint is rate-limited per email and per connection.

    B — Present it

    curl -i https://eleviq-lab-gateway.gateway-worker.workers.dev/api/delegate/account \
  -H 'Signature-Input: …' -H 'Signature: …' -H 'Signature-Agent: …' \
  -H 'X-Acting-For: you@example.com' -H 'X-Delegation-Code: 482913'

    Drop X-Delegation-Code, or change one digit, to see the other two outcomes. Codes are single-use and expire after 5 minutes.
