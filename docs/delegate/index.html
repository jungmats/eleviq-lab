1 The problem

Demo 1 proved a specific key signed this request. Demo 2 proved that key is allowed to do this. Neither proves who the request is for — a fully verified, fully permitted agent can still be lying about which person it claims to act on behalf of.

This lab's answer, pragmatic rather than complete (OAuth can come later): a one-time code. An agent claiming to act for a specific email address only gets access once it presents a code sent to that address — proof of an inbox, not proof that an email address was typed correctly.

This demo simulates the email step: the code appears directly on this page instead of being sent anywhere, so the mechanism is visible without needing a real inbox. A real deployment would only ever email it.

    3 Test it from your own tools

    The console above is a convenience. The gateway is a plain public HTTP API — two calls, same signed identity as Demo 1 on both.

    A — Request a code

    # sign this the same way as /api/sign in Demo 1
curl -s -X POST https://eleviq-lab-gateway.gateway-worker.workers.dev/api/delegate/request-code \
  -H 'Signature-Input: …' -H 'Signature: …' -H 'Signature-Agent: …' \
  -H 'content-type: application/json' \
  -d '{"acting_for":"jane@example.com"}'

    Returns the code directly — DEMO only; a real deployment would email it and never put it in this response.

    B — Present it

    curl -i https://eleviq-lab-gateway.gateway-worker.workers.dev/api/delegate/account \
  -H 'Signature-Input: …' -H 'Signature: …' -H 'Signature-Agent: …' \
  -H 'X-Acting-For: jane@example.com' -H 'X-Delegation-Code: 482913'

    Drop X-Delegation-Code, or change one digit, to see the other two outcomes. Codes are single-use and expire after 5 minutes.
