1 The problem

Demo 1 answered "is this really who it says it is?" Even if the answer is yes, that leaves a different question open: is it allowed to do a certain action, or access a certain resource?

A website can state an answer in two places:

  • robots.txt, extended with a new signal called Content Signals: a simple yes or no for each type of use — search, live AI answers, or AI training.
  • A license file in a format called Really Simple Licensing (RSL) — a short, machine-readable way to spell out exactly what's allowed, refused, or requires payment.

Both are real files, served by this lab's gateway. You can view them here: /robots.txt and /.well-known/rsl.xml.

Publishing this doesn't stop anything by itself — a request can simply ignore it. This demo shows how a server enforces the policy instead: checking each request and blocking the ones that violate it.

This is an unlisted lab page — not indexed, no inbound links. The API endpoint it calls is public on purpose.

2 The demo

Every request below uses the same signed identity as Demo 1. What changes is only what the agent says it plans to do with the resource — sent as a header we call X-Agent-Purpose (our own convention for this demo, not a standard). Its three possible values match the same three uses from robots.txt and RSL above: search, live AI answers (ai-input), and AI training (ai-train).

The agent requests a protected resource — Q3 sales notes. Choose what it says it plans to do, then send the request and see the server's decision.

    3 Stated vs enforced

    Both panels below are fetched live, not hardcoded.

    Stated (fetched live)

    GET /robots.txt

    Loading…

    GET /.well-known/rsl.xml

    Loading…

    Enforced (this gateway's actual decision)

    • ai-input and search are declared permitted — a request declaring either is actually allowed (200).
    • ai-train is declared prohibited — a request declaring it is actually refused (403), even from the exact same trusted identity that was just allowed for ai-input.
    • No purpose declared → refused (403). The Content Signals spec itself treats a missing answer as neutral — neither allowed nor refused. This gateway is stricter: no answer means no.

    The panel on the left and this decision use the exact same policy data, so they can't drift apart. But publishing a policy doesn't enforce it — that happens above, in section 2.

    4 Test it from your own tools

    The console above is a convenience. The gateway is a plain public HTTP API.

    A — Ask an AI assistant

    Fetch https://eleviq-lab-gateway.gateway-worker.workers.dev/api/decide/deal-notes,
tell me what it returns and why, then try again declaring a different
X-Agent-Purpose (ai-input, ai-train, or none at all).

    B — Unsigned · nothing to install

    curl -i https://eleviq-lab-gateway.gateway-worker.workers.dev/api/decide/deal-notes

    Returns 401 — Demo 2 still requires the same signed identity as Demo 1 before it even considers a policy question.

    C — Signed via the test helper · just curl

    # 1 · ask the gateway to sign a request for you
#     (a test aid — NOT part of the security model)
curl -s -X POST https://eleviq-lab-gateway.gateway-worker.workers.dev/api/sign \
  -H 'content-type: application/json' \
  -d '{"url":"https://eleviq-lab-gateway.gateway-worker.workers.dev/api/decide/deal-notes"}'

# 2 · replay the three headers it returns, adding the declared purpose
curl -i https://eleviq-lab-gateway.gateway-worker.workers.dev/api/decide/deal-notes \
  -H 'Signature-Input: …' -H 'Signature: …' -H 'Signature-Agent: …' \
  -H 'X-Agent-Purpose: ai-train'

    Try ai-input, ai-train, and dropping the header entirely to see all three outcomes.

    D — Signed client-side · the real reference code (Node.js 18+)

    mkdir wba && cd wba
npm init -y && npm install web-bot-auth

curl -O https://lab.eleviq.solutions/reference/sign-request.mjs
curl -O https://lab.eleviq.solutions/reference/demo-agent.jwk.json

node sign-request.mjs \
  --url https://eleviq-lab-gateway.gateway-worker.workers.dev/api/decide/deal-notes \
  --key demo-agent.jwk.json --send

    The X-Agent-Purpose header travels unsigned, by design — same as X-Demo-Agent-Claim in Demo 1. Add it to the request with your HTTP client of choice alongside the signature headers the script prints.
